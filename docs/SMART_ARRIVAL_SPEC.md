# WalkLab Smart Arrival 단계별 명세

- 문서 상태: 로드맵 기준 명세
- 작성일: 2026-10-30
- 대상 단계: G8~G17
- 선행 문서: `MVP.md`, `PRD.md`, `SPEC.md`, `PLAN.md`, `docs/G6_MOVEMENT_ANALYSIS.md`, `docs/G7_WALKING_SPEED_MODEL.md`

## 1. 목적과 현재 기준선

이 문서는 첫 GPS 수집 MVP 이후 Smart Arrival을 단계적으로 구현하기 위한 제품·기술 경계를 정의한다. 각 단계는 이전 단계의 검증된 결과만 사용하며, 외부 API의 제공 범위·계약·요금·호출 제한·라이선스·브라우저 호출 가능 여부가 확인되지 않은 내용은 `검증 필요`로 표시한다.

현재 기준선은 다음과 같다.

- G1~G6은 구현과 실제 iPhone Safari 검증을 완료했다.
- G7 `recency-weighted-v1`은 구현·배포했고, 기존 학습 결과 표시와 신규 완료 세션 동기화 후 개인 추정속도·학습 가중치 자동 갱신을 iPhone Safari에서 확인했다.
- GPS 원본, IndexedDB 우선 저장, Supabase Auth·RLS·동기화, 사용자별 데이터 격리 원칙은 모든 후속 단계에서 유지한다.

## 2. 공통 사용자 시나리오

1. 사용자는 이메일 OTP로 로그인한다.
2. 출발지·도착지 또는 약속 장소와 목표 도착시각을 입력한다.
3. WalkLab은 사용 가능한 속도 모델과 경로·교통 데이터를 조합해 ETA와 출발 계획을 제시한다.
4. 실제 이동 중에는 사용자가 화면을 켜 둔 전면 실행 범위에서 현재 위치와 속도로 ETA를 갱신한다.
5. 사용자가 보행을 완료하고 기록이 동기화되면 이후 계산에서 G7 개인 속도 모델이 다시 계산된다.
6. 데이터가 부족하거나 외부 정보가 오래된 경우 확정값처럼 표시하지 않고 사용한 기준, 표본 수, 갱신 시각과 불확실성을 함께 표시한다.

## 3. 확장 가능한 ETA 계산 구조

### 3.1 구성요소

| 구성요소 | 책임 | 대표 입력 | 대표 출력 |
|---|---|---|---|
| `SpeedProfile` | 적용할 기본 보행속도 선택 | 기본값, G7 결과, 향후 G17 결과 | 속도, 출처, 신뢰 상태, 모델 버전 |
| `WalkingRoute` | 도보 경로와 구간 제공 | 출발·도착 좌표 | 구간 거리·형상·경로 메타데이터 |
| `WalkingTimeEstimator` | 도보 구간 시간 계산 | 경로, `SpeedProfile`, 경사·날씨 보정 | 도보시간과 구간별 근거 |
| `SignalWaitEstimator` | 횡단보도 대기시간 계산 | 교차 지점, 시각, 신호 데이터 | 별도 신호 대기시간 |
| `TransitPlanner` | 대중교통 승차·환승·하차 계산 | 출발·도착·출발/도착 목표시각 | 대기·승차·환승·도보 leg |
| `LiveEtaUpdater` | 전면 측정 중 잔여 ETA 갱신 | 현재 위치·속도, 선택 경로, 최신 교통정보 | 갱신 ETA·필요 보행속도 |
| `ArrivalPlanComposer` | 구성요소를 한 번씩 조합 | 위 계산 결과 | 도착예정, 추천 출발, 여유시간, 근거 |

### 3.2 속도 모델 선택 순서

1. 개인 데이터가 부족한 신규 사용자는 제품 설정으로 관리하는 검증된 기본 보행속도를 사용한다. 기본값 자체는 G8 착수 때 실제 보행 검증 후 확정한다.
2. G7 최소 학습 기준을 충족하면 `recency-weighted-v1` 결과를 사용한다.
3. G17 후보 모델은 시간순 검증에서 G7보다 우수하고 안전 기준을 통과한 경우에만 선택한다.
4. G7 모델은 G17 도입 후에도 비교 기준과 장애·회귀 시 대체 수단으로 유지한다.

### 3.3 중복 계산 방지 규칙

- 기본 도보시간은 각 도보 leg마다 한 번만 계산한다.
- 경사도와 날씨는 `WalkingTimeEstimator` 안에서 기본 보행속도 또는 구간시간을 보정한다. 보정한 뒤 같은 영향을 별도 시간으로 다시 더하지 않는다.
- 횡단보도 신호 대기는 걷는 시간과 분리해 한 번만 가산한다. GPS에서 감지된 과거 정지시간을 미래 신호 대기시간에 그대로 중복 반영하지 않는다.
- 대중교통 접근·환승·하차 후 도보 leg는 `WalkingTimeEstimator`에 한 번씩만 전달한다.
- 실시간 도착정보가 유효하면 같은 차량의 시간표 기반 대기·도착값을 **대체**한다. 두 값을 더하지 않는다.
- 외부 API가 이미 환승 도보나 대기시간을 포함하는지 공급자별 계약에 기록한다. 포함 여부가 불명확하면 계산에 사용하지 않고 `검증 필요`로 처리한다.
- 모든 결과에 입력 시각, 데이터 출처, 공급자 응답 ID, 알고리즘 버전과 데이터 갱신 시각을 붙여 재현 가능하게 한다.

### 3.4 공통 데이터 계약

```text
EtaEstimate
  calculatedAt
  arrivalAt
  totalSeconds
  confidenceStatus
  components[]
    type: walking | signal_wait | transit_wait | transit_ride | transfer | buffer
    durationSeconds
    source
    sourceUpdatedAt
    algorithmVersion
  speedProfile
    source: default | recency_weighted_v1 | future_ml
    speedMps
    sampleCount
```

실제 TypeScript 타입과 저장 여부는 각 단계의 SPEC에서 확정한다. GPS 원본과 ETA 파생 결과는 분리하며, ETA 재계산을 위해 GPS 원본을 수정하지 않는다.

## 4. G8 — 도보 경로 탐색 및 개인화 ETA

### 목적과 사용자 시나리오

사용자가 출발지와 도착지를 고르면 도보 경로를 지도에 표시하고, 기본속도 또는 G7 개인속도로 예상 보행시간과 도착시각을 계산한다.

### 입력·출력

- 입력: 출발·도착 좌표, 계산 기준시각, 현재 사용자의 G7 모델 상태
- 출력: 도보 경로 형상, 거리, 적용 속도와 출처, 개인화 ETA, 계산 시각

### 외부 API·의존성

- 경로 표시: 기존 카카오맵 JavaScript SDK 재사용
- 장소 검색·좌표 입력: 카카오 로컬 API 후보 — 쿼터·약관·키 노출 방식 `검증 필요`
- 보행자 경로: 카카오맵 REST API `GET /v2/routing/walk`를 서버 함수에서 호출한다. 실제 앱 권한·요금·쿼터와 운영 호출 성공 여부는 `검증 필요`
- 카카오맵 JavaScript SDK는 장소 검색과 표시 계층, 카카오맵 REST API는 도보 경로 공급자로 역할을 분리한다.

### G1~G7 연결

- G1 사용자 인증과 RLS 경계를 유지한다.
- G5 지도와 한국 시간 표시를 재사용한다.
- G7에서 `ready`이면 개인속도, 아니면 기본속도를 선택한다.

### 구현 범위·제외 범위

- 포함: 단일 도보 경로, 거리와 ETA, 속도 출처·데이터 부족 표시, 지도 경로
- 제외: 실시간 재계산, 목표 도착시각, 대중교통, 신호·경사·날씨 보정

### 완료 기준·실기기 테스트

- 같은 입력과 모델 버전에서 같은 ETA가 계산된다.
- 기본속도와 G7 속도 선택 조건이 테스트된다.
- 경로 API 실패 시 직선거리로 확정 ETA를 만들지 않고 오류·재시도를 표시한다.
- iPhone Safari에서 장소 선택, 경로 표시, 확대·축소, ETA와 속도 출처를 확인한다.
- 실제 걸은 시간과 예측값을 비교할 수 있는 검증 기록을 남긴다.

## 5. G9 — 실시간 ETA 갱신 및 추천 보행속도

### 목적과 사용자 시나리오

사용자가 선택한 경로를 걷는 동안 현재 위치와 최근 유효 보행속도로 남은 ETA를 갱신하고, 목표가 있을 때 필요한 평균 보행속도를 제시한다.

### 입력·출력

- 입력: G8 경로, 전면 실행 중 GPS, `quality-v1`, 현재 시각, 선택적 목표 도착시각
- 출력: 남은 거리·ETA, 현재 유효속도, 추천 보행속도, 경로 이탈·데이터 불확실 상태

### 외부 API·의존성

- 기존 `watchPosition()`과 품질 판정 재사용
- 경로 재탐색 정책과 API 재호출 비용 `검증 필요`

### G1~G7 연결

- G2 원본 저장과 watcher 중복 방지를 유지한다.
- G6 판정 불가 구간을 정지로 단정하지 않는다.
- G7 속도는 초기 기준이며 실시간 관측값과 별도 출처로 관리한다.

### 구현 범위·제외 범위

- 포함: Safari 화면이 열린 동안의 갱신, 남은 구간 기준 계산, 비현실적 추천속도 경고
- 제외: 화면 잠금·백그라운드 GPS 보장, 자동 경로 변경, 안전을 해치는 속도 독촉

### 완료 기준·실기기 테스트

- GPS 콜백이 없어도 임의 위치를 만들지 않는다.
- 품질 제외 지점 하나로 ETA가 급변하지 않도록 검증한다.
- 추천속도의 계산 근거와 달성 불가 상태가 표시된다.
- iPhone Safari 전면 실행에서 이동·정지·수신 공백 시 ETA 상태를 확인한다.
- 화면 잠금·앱 전환 중 동작은 보장하지 않는다고 표시한다.

## 6. G10 — 목표 도착시각 및 추천 출발시간

### 목적과 사용자 시나리오

사용자가 약속 장소와 목표 도착시각을 입력하면 예상 이동시간과 여유시간을 반영한 추천 출발시각을 받는다.

### 입력·출력

- 입력: 장소/좌표, 목표 도착시각, 출발지, G8 ETA, 제품 설정의 준비·안전 여유시간
- 출력: 추천 출발시각, 남은 준비시간, 지금 출발 필요 여부, 사용한 여유시간

### 외부 API·의존성

- 장소 검색은 G8에서 선택한 공급자 재사용
- 브라우저·서버 시간대와 휴대폰 시계 오차 처리 방식 `검증 필요`

### G1~G7 연결

- G5의 `Asia/Seoul` 표시 원칙과 UTC 저장 원칙을 유지한다.
- G7 데이터 부족 상태를 추천 출발 결과에 전파한다.

### 구현 범위·제외 범위

- 포함: 한 장소·한 목표시각, 도보 기준 추천 출발, 과거 시각·시간대 오류 처리
- 제외: 대중교통, 반복 약속, 캘린더 연동, 출발 알림

### 완료 기준·실기기 테스트

- `추천 출발 = 목표 도착 - 예상 이동 - 명시적 여유시간`이 시간대 경계에서도 재현된다.
- 자정 전후와 이미 늦은 경우를 테스트한다.
- iPhone Safari에서 장소·시각 입력, 키보드와 시간 선택 UI, 결과 갱신을 확인한다.

## 7. G11 — 버스·지하철 경로 탐색 및 환승시간

### 목적과 사용자 시나리오

사용자가 목적지까지 가능한 버스·지하철 경로와 접근 도보·환승·하차 후 도보를 포함한 예상시간을 비교한다.

### 입력·출력

- 입력: 출발·도착 좌표, 출발 또는 도착 기준시각, 교통수단 조건
- 출력: 경로 후보, leg 목록, 접근·환승 도보, 대기·승차·환승시간, 총 예상시간

### 외부 API·의존성

- ODsay 대중교통 길찾기 또는 TMAP 대중교통 후보 — 지원 지역·요금·호출 제한·시간표 반영 범위·상업 이용 조건 `검증 필요`
- API 키 보호와 여러 응답 조합을 위해 서버리스/BFF가 필요한지 `검증 필요`

### G1~G7 연결

- 모든 도보 leg는 G8 `WalkingTimeEstimator`와 G7 속도 선택 규칙을 사용한다.
- 사용자 계정과 저장 계획은 기존 RLS 경계를 벗어나지 않는다.

### 구현 범위·제외 범위

- 포함: 버스·지하철 경로 후보와 환승시간, 도보 leg의 개인화
- 제외: 실시간 도착정보, 알림, 차량 위치, 예약·결제

### 완료 기준·실기기 테스트

- 공급자가 반환한 포함 시간과 WalkLab이 추가한 시간을 항목별로 구분한다.
- 접근·환승 도보시간이 두 번 더해지지 않는다.
- 경로 없음·부분 응답·지역 미지원 상태를 처리한다.
- iPhone Safari에서 실제 익숙한 경로와 정류장·역·환승 순서를 비교한다.

## 8. G12 — 시간표 및 실시간 도착예정정보

### 목적과 사용자 시나리오

선택한 대중교통 경로에 시간표와 가능한 실시간 도착예정정보를 연결해 실제 탑승 가능성과 ETA를 갱신한다.

### 입력·출력

- 입력: G11의 노선·정류장/역 식별자, 현재 시각, 시간표, 실시간 응답
- 출력: 예정/실시간 구분, 예상 대기시간, 탑승 후보, 데이터 갱신 시각과 신선도

### 외부 API·의존성

- 국토교통부 TAGO 버스도착정보와 지역별 버스 API 후보 — 제공 도시·식별자 매핑·운영 트래픽 `검증 필요`
- 지하철 시간표·실시간 정보는 지역별 공식 API 후보 — 도시별 범위와 지연정보 제공 여부 `검증 필요`
- G11 공급자의 실시간 API 조합 가능 여부와 이용 약관 `검증 필요`

### G1~G7 연결

- G4의 재시도 개념은 참고하되 GPS 동기화 큐와 외부 교통 캐시는 분리한다.
- 개인 도보속도로 정류장/역 도착 가능 시각을 계산한다.

### 구현 범위·제외 범위

- 포함: 시간표와 실시간 값의 출처·신선도 표시, 가능한 교통편 판정
- 제외: 정보가 없는 지역에 대한 가짜 실시간값, 예약·발권, 운행 보장

### 완료 기준·실기기 테스트

- 유효한 실시간 값은 같은 항목의 시간표 값을 대체하고 중복 가산하지 않는다.
- 오래된 응답은 실시간으로 표시하지 않는다.
- 식별자 매핑 실패와 공급자 장애 시 시간표 기반/정보 없음 상태를 구분한다.
- iPhone Safari에서 실제 정류장 전광판·공식 앱과 시각 및 갱신 시점을 비교한다.

## 9. G13 — 출발 알림 및 교통편 변동 재계산

### 목적과 사용자 시나리오

추천 출발시각이 가까워지면 알리고, 선택한 교통편의 지연·취소·도착 변경이 감지되면 계획을 다시 계산한다.

### 입력·출력

- 입력: G10 출발 계획, G12 데이터와 신선도, 알림 권한·앱 실행 상태
- 출력: 출발 알림, 변경 사유, 갱신된 출발시각·ETA·대체 경로

### 외부 API·의존성

- iOS의 Web Push는 홈 화면에 추가된 웹 앱과 사용자 동작에 따른 권한 요청이 기본 전제다. 대상 iOS 버전·설치 형태·권한 UX·백그라운드 전달 신뢰성은 `검증 필요`
- 안정적 서버 예약 작업과 푸시 발송이 필요할 경우 서버리스 또는 네이티브 iOS 전환 `검증 필요`

### G1~G7 연결

- 사용자 식별은 G1을 사용하되 인증 토큰을 알림 payload에 포함하지 않는다.
- 기존 웹의 백그라운드 GPS 비보장 원칙을 유지한다.

### 구현 범위·제외 범위

- 포함: 권한을 명시적으로 받은 알림, 전면 실행 중 재계산, 변경 근거 표시
- 제외: 권한 없는 알림, Safari 종료 상태에서의 무조건적 전달 보장, 자동 예약 변경

### 완료 기준·실기기 테스트

- 같은 변경 이벤트로 중복 알림이 발생하지 않는다.
- 오래된 교통정보로 출발시각을 되돌리지 않는다.
- iPhone Safari의 지원 OS·설치 형태별 알림 수신을 실기기에서 확인한다.
- 보장할 수 없는 환경에서는 앱 내 알림으로 명확히 대체한다.

## 10. G14 — 횡단보도·신호 대기시간 정밀화

### 목적과 사용자 시나리오

도보 경로의 횡단보도와 시간대별 신호 대기를 별도 구성요소로 추정해 ETA를 개선한다.

### 입력·출력

- 입력: 경로와 교차 지점, 통행 방향, 시각, 이용 가능한 신호 데이터 또는 검증된 통계
- 출력: 교차 지점별 예상 대기시간, 총 신호 대기, 출처와 신뢰 상태

### 외부 API·의존성

- 전국 범위의 보행 신호·주기 데이터 제공 여부와 이용 조건 `검증 필요`
- 지역별 공공데이터 또는 사용자 과거 정지 패턴의 활용 가능성과 개인정보 영향 `검증 필요`

### G1~G7 연결

- G6에서 감지한 정지 구간은 연구·검증 자료로만 사용하며 신호 대기로 자동 단정하지 않는다.
- 원본 GPS와 이동 분류는 변경하지 않는다.

### 구현 범위·제외 범위

- 포함: 확인 가능한 교차 지점과 버전 있는 대기 추정, 데이터 없음 상태
- 제외: 정지를 신호·혼잡·휴식으로 임의 분류, 신호 위반을 유도하는 카운트다운

### 완료 기준·실기기 테스트

- 신호 대기는 도보시간과 분리해 한 번만 더한다.
- 데이터 없는 교차로에 확정값을 만들지 않는다.
- 같은 경로를 여러 번 걸어 예측과 실제 대기시간을 비교한다.
- iPhone Safari에서 신호 대기 포함/제외 근거를 확인한다.

## 11. G15 — 오르막·내리막 경사도 보정

### 목적과 사용자 시나리오

경로의 방향별 고도 변화를 반영해 평지 기준 개인속도를 오르막·내리막 구간에 맞게 보정한다.

### 입력·출력

- 입력: 경로 구간, 신뢰 가능한 고도/경사 프로필, G7 기본속도
- 출력: 구간 경사, 방향별 속도 보정, 보정 도보시간과 데이터 품질

### 외부 API·의존성

- 국내 경로 고도 프로필 공급자·해상도·좌표계·요금·라이선스 `검증 필요`
- iPhone GPS altitude만으로 경로 고도를 확정할 수 있는지 정확도 검증 필요

### G1~G7 연결

- 저장된 원본 altitude는 보존하고 파생 경사와 모델 버전을 분리한다.
- G7 평지/혼합 속도에서 경사 효과를 분리할 데이터가 충분한지 먼저 평가한다.

### 구현 범위·제외 범위

- 포함: 구간별 방향성 경사 보정, 결측 시 무보정 fallback
- 제외: 경사 데이터를 만들기 위한 원본 고도 덮어쓰기, 데이터 없이 개인 경사 모델 확정

### 완료 기준·실기기 테스트

- 같은 길의 반대 방향에서 오르막·내리막이 뒤바뀐다.
- 경사 보정은 도보속도에 한 번만 적용된다.
- 평지·오르막·내리막 실보행을 반복해 오차 변화를 비교한다.
- 고도 데이터가 없거나 불안정하면 기본 ETA로 안전하게 돌아간다.

## 12. G16 — 날씨에 따른 보행속도 보정

### 목적과 사용자 시나리오

예상 이동 시간대의 비·눈·기온·바람 등 확인 가능한 날씨가 보행속도에 미치는 영향을 보정한다.

### 입력·출력

- 입력: 경로 위치·예상 이동 시각, 예보/관측, G7 또는 G15 속도
- 출력: 날씨 상태, 적용 보정, 보정 ETA, 예보 발표·기준시각

### 외부 API·의존성

- 기상청 단기예보 조회서비스 후보 — 격자 변환·발표시각·쿼터·운영 사용 조건 `검증 필요`
- 강수·적설·폭염 등 안전 안내 기준과 지역 차이 `검증 필요`

### G1~G7 연결

- 과거 보행 기록에 날씨 정보가 없으면 GPS만으로 당시 날씨를 추측하지 않는다.
- G7 속도를 원래 상태로 유지하고 날씨 보정 결과를 별도 파생값으로 둔다.

### 구현 범위·제외 범위

- 포함: 출처·시각이 있는 예보 보정, 데이터 없음/오래됨 표시, 안전 안내
- 제외: 날씨 예측 자체 생성, 개인별 날씨 모델을 근거 없이 학습

### 완료 기준·실기기 테스트

- 날씨 보정은 각 도보 leg에 한 번만 적용된다.
- 예보가 오래되거나 실패하면 무보정 ETA와 상태를 표시한다.
- 동일 경로의 맑음/강수 조건에서 계산 근거와 실제 오차를 비교한다.
- iPhone Safari에서 위치·시간대에 맞는 발표시각과 단위를 확인한다.

## 13. G17 — 조건부 머신러닝 모델

### 목적과 사용자 시나리오

충분한 사용자·경로·상황 데이터가 축적되고 기존 G7보다 성능이 좋다는 증거가 있을 때만 개인 보행속도 또는 ETA 모델을 교체한다.

### 입력·출력

- 입력: 세션 단위 학습 사례, 시간순 분할, 품질·이동 분석, 선택적으로 검증된 경사·날씨 특징
- 출력: 예측값, 모델 버전, 평가 지표, 적용/보류 판정, fallback 모델

### 외부 API·의존성

- Python 학습·평가 환경과 모델 배포 방식 `검증 필요`
- FastAPI, 서버리스 추론 또는 사전 계산 중 운영 방식 `검증 필요`
- 모델·특징 저장소, 개인정보 보존기간과 삭제 전파 `검증 필요`

### G1~G7 연결

- GPS 지점이 아니라 세션을 학습 단위로 삼는다.
- G7의 시간순 백테스트와 가중평균을 기준선으로 유지한다.
- 삭제된 사용자 데이터는 재학습 데이터와 파생 모델에서도 제거 가능한 구조를 요구한다.

### 진입 조건

- 사전에 정한 최소 세션·사용자·상황 표본 수를 충족한다.
- 미래 데이터 누수 없는 시간순 검증이 가능하다.
- G7 대비 평균절대오차와 큰 오차 비율 등 사전 정의 지표에서 일관된 개선을 보인다.
- 느린 정상 보행을 이상치로 제거하지 않는 공정성·안전성 검토를 통과한다.
- 실패 시 즉시 G7 또는 기본속도로 돌아갈 수 있다.

### 구현 범위·제외 범위

- 포함: 후보 모델의 오프라인 학습, shadow 비교, 버전·재현성·fallback
- 제외: 일정만으로 강제 도입, 정확도 증거 없는 자동 전환, G7 제거, GPS 원본 변경

### 완료 기준·실기기 테스트

- 같은 학습 스냅샷과 버전에서 결과를 재현한다.
- 시간순 holdout에서 G7보다 나은 성능을 입증하고 표본 수를 표시한다.
- 모델 장애·결측 특징·신규 사용자에서 G7 또는 기본속도로 전환된다.
- 실제 iPhone Safari에서는 모델 출처와 데이터 부족 상태가 정확히 표시된다.
- 신규 기록 후 재학습/재계산과 삭제 요청 전파를 종단 검증한다.

G17은 위 조건을 충족하기 전에는 시작하지 않으며 고정 일정으로 약속하지 않는다.

## 15. 공통 보안·운영 완료 조건

- 브라우저에는 공개가 허용된 키만 두며 Secret·Service Role·외부 API 비밀 키를 포함하지 않는다.
- 사용자별 저장 데이터는 기존 Supabase Auth와 RLS 경계를 유지한다.
- 외부 API 응답은 GPS 원본과 분리하고 출처·시각·버전을 기록한다.
- 외부 장애 시 임의 값을 만들지 않고 마지막 값의 신선도 또는 사용할 수 없음 상태를 표시한다.
- 각 단계는 typecheck, lint, 전체 Vitest, production build와 Windows 브라우저·실제 iPhone Safari 검증을 통과해야 한다.
- 새 DB 테이블·컬럼, 서버 구성 또는 환경변수가 필요하면 구현 전에 이유·보안 경계·migration·rollback을 별도 제안하고 승인받는다.
- G8 이후 기능을 구현하더라도 G1~G7 회귀 테스트와 GPS 원본 무결성 검증을 유지한다.
