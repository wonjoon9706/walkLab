# G8 도보·부분 개인화 ETA 차단 수정

후속 운영 정책: [서울시 API 운영 허용](SEOUL_API_PRODUCTION.md). 아래 운영 차단 시나리오는 이전 단계의 실패 처리 검증 이력이며, 현재는 서울시 서버 호출의 환경별 차단을 제거했다.

## 수정 범위

- `KakaoTransitRoutePanel.tsx`: 계산 결과와 도보 확보 범위를 분리한다. 계산식은 그대로다.
  - 계산 `available` + 접근/하차 G8 증거 모두 확보 + 실제 정류장 대신 원본 BUS 끝점을 사용한 참고값이 아님: `complete`, 기존 `개인화 추정` 표시.
  - 계산 `available`이지만 한쪽 G8만 있거나 명시 WALKING만 있거나 원본 BUS 끝점 참고 도보 포함: `partial`, `부분 개인화 참고` 표시.
  - 유효한 계산 결과 없음: `unavailable`.
- 부분 결과도 목록·상세·선택 캐시에 같은 값을 사용한다. 미반영된 출발/하차 도보 또는 정류장 연결 미확인 상태를 안내한다.
- 완전/부분의 구분은 **G8 외부 도보 반영 범위**다. 역사 내부시간·실시간 대기를 확정한 전체 실시간 ETA를 의미하지 않는다.
- 부분 결과와 전체 도보 반영 결과를 섞어 개인화 최단순으로 정렬하지 않는다. 기존 우선 3개·더보기·제한 병렬·캐시는 유지한다.

## 지하철 하차 스냅

`automaticTransitEgress.ts`에서 출입구 추천이 없더라도 역명·노선·출구·폐쇄 조건을 통과하고 G8이 성공한 후보의 스냅 초과가 있으면 `detailReason=WALKING_ENDPOINT_MISMATCH`를 붙인다.
기존 ETA 증거 수집과 참고 지도선 생성 함수를 그대로 재사용한다. 유효 G8 후보가 하나일 때만 ETA 증거로 채택한다.
복수 후보는 임의 선택하지 않는다. 참고선은 실제 G8 polyline만 그리고 미확인 연결선을 추가하지 않는다. BUS Egress의 공통 끝점 예외는 [복수 후보 참고 도보 정책](EGRESS_MULTIPLE_REFERENCE.md)을 따른다.

## 버스 검증과 참고 도보 분리

`transitPathReferenceWalk.ts`는 서울시 검증 실패/차단 또는 검증 후보 없음에서만 사용할 작은 공통 조회 함수다.

- 입력은 해당 첫/마지막 BUS step의 실제 원본 polyline 끝점이다.
- BUS 수단, 단일 차량명, 승하차 이름, 최소 두 개의 유효한 경로 좌표, 서로 다른 구간 끝점, 요청 출발/목적 좌표를 검사한다.
- 좌표가 없거나 비정상이면 임의 목표를 만들지 않는다. Access의 복수 차량 제한은 유지하며, BUS Egress는 공통 참고 위치가 확인되는 경우에만 위 정책에 따라 원본 끝점 참고 도보를 허용한다.
- 실제 G8 API에 요청하고 거리·공급자 시간·polyline·스냅 오차를 보존한다. 직선 도보를 생성하지 않는다.
- 결과는 `referenceWalk`에 저장하며 실제 `busCandidates`나 `ready` 탑승 위치에 넣지 않는다.
- 출처 `kakao_bus_path_endpoint`, 원본 step index, 접근/하차 scope, 요청 양 끝 좌표, `unverified_boarding_point`를 보존한다.
- 같은 기존 G8 요청 캐시·예산을 사용한다. 외부 검증 실패 시 참고 G8 요청이 접근/하차별로 추가될 수 있으며 전체 검색 예산을 늘리지는 않는다.
- 기존 `kakaoTransitEta`의 유효 경로 검사·도보 시간 치환·중복 방지·G7 속도 정책을 재사용한다. 카카오 total에 G8 시간을 단순 더하지 않는다. 기존 공급자 기본 도보시간 포함 가정은 여전히 추정 모델이다.

이 참고 좌표는 실제 버스 정류장/승차 방향/접근 가능 출입구를 증명하지 않는다. GPS 자동 종료와 탑승 가능성 판단에는 사용하지 않는다.
기존 `resolveTransitRecordingTarget`이 검증된 실제 후보만 읽으며, 검증 후보가 없으면 자동 종료 목표는 null이고 수동 종료를 안내한다.

## 진단

개발 진단에서 다음 원인을 분리한다. 실제 좌표·인증정보·요청 URL 로그는 추가하지 않았다.

| 코드 | 의미 |
| --- | --- |
| `PRODUCTION_DISABLED` | 운영 API 차단 |
| `STOP_CANDIDATES_EMPTY` | 검증된 정류장 후보 없음 |
| `STOP_DIRECTION_MISMATCH` | 노선의 ID/정류장 순서 불일치 |
| `MULTIPLE_CANDIDATES` | 복수 위치/차량 후보 |
| `STOP_API_FAILED` | 정류장 검증 공급자 조회 실패 |
| `G8_REQUEST_FAILED` | G8 조회 실패 |
| `G8_SNAP_MISMATCH` | G8 성공 후 연결 스냅 기준 초과 |
| `G8_EVIDENCE_EXCLUDED` | 비정상 경로이거나 단일 ETA 증거로 채택할 수 없음 |

`diagnosticCode`와 `referenceWalkIssue`를 별도로 보존하므로 운영 차단 후 참고 G8 실패도 두 원인을 함께 확인할 수 있다.
일반 화면에는 부분 반영·미반영 구간·실제 정류장 연결 미확인 등 쉬운 안내를 표시한다.

## 검증

TypeScript, ESLint, 전체 Vitest 87개 파일/493개 테스트, Production build 및 서버 ESM 검사 통과. 서버 함수는 6/12개다.
기존 번들 크기 경고는 남는다. 실제 외부 API·브라우저·iPhone 이동 검증은 수행하지 않았다.

테스트는 다음을 포함한다.

- 접근 G8만 있을 때 목록/상세의 같은 부분 ETA와 하차 미반영 안내
- 양쪽 G8 증거의 기존 개인화 추정 및 지하철 하차 단일 스냅 실패 참고선 전달
- 실제 지도 컴포넌트에서 G8 polyline만 별도 스타일로 추가하고 미확인 연결선을 만들지 않음
- 운영 정류장 차단 시 참고 도보를 보존하되 자동 종료 목표를 생성하지 않음
- 원본 좌표 누락/비정상, 복수 차량, 취소, G8 실패/빈 polyline
- 기존 3개 카드·더보기, G7/G8 ETA, GPS 자동 저장 회귀

## 로컬 확인

1. `vercel dev`에서 허용된 사용자로 출발·목적지를 설정한다.
2. 한쪽 도보만 확보되는 경로에서 `부분 개인화 참고`, 미반영 구간, 카카오 기본시간을 비교한다.
3. 상세로 이동해 목록과 같은 ETA, 추정 도보 타임라인 및 참고 지도선을 확인한다.
4. 개발 진단에서 정류장 검증 원인과 G8 요청/스냅 결과를 구분한다.
5. 원본 BUS 끝점만 이용한 참고 경로에서는 정류장 연결 미확인과 자동 종료 비활성화를 확인한다.
6. 정상 검증된 탑승 지점의 기존 자동 저장·수동 종료는 별도로 실제 이동 테스트한다.

서울시 HTTP의 Production/Preview 제한은 유지한다. 카카오 경로가 성공해도 실시간 버스·지하철이 운영에서 사용 가능해진 것은 아니다.
